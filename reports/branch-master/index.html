🚨 Arbitrary Command Execution via Subprocess with shell=True

test_samples/vulnerable_app.py:27
bandit code_vulnerability B602
HIGH

A subprocess.Popen call uses `shell=True`, which allows arbitrary command execution if an attacker can control any part of the command string passed to the function.

Risk: This severe vulnerability allows an attacker to execute arbitrary operating system commands with the privileges of the application, potentially leading to full system compromise, data theft, or denial of service.

Fix: Set `shell=False` in `subprocess.Popen` calls and pass the command and its arguments as a list of strings. If shell features are absolutely necessary, ensure all user-controlled input is strictly validated and sanitized, or use `shlex.quote` for arguments, though `shell=False` is generally preferred.

Fix security finding B602 in test_samples/vulnerable_app.py:27. Issue: Subprocess call with shell=True enables arbitrary command execution.

🚨 Use of Cryptographically Weak Hashing Algorithm (MD5)

test_samples/vulnerable_app.py:32
bandit code_vulnerability B324
HIGH

The application uses the MD5 hashing algorithm for security-sensitive operations. MD5 is cryptographically broken and vulnerable to collision attacks, making it unsuitable for secure applications.

Risk: Using MD5 for security purposes (e.g., password storage, digital signatures, integrity checks) can allow attackers to forge data, bypass authentication, or compromise data integrity due to its known weaknesses and susceptibility to collision attacks.

Fix: Replace MD5 with a modern, cryptographically strong hashing algorithm such as SHA-256, SHA-3 (e.g., `sha256`, `sha512` from `hashlib`), or bcrypt/scrypt for password storage. Ensure `usedforsecurity=False` is explicitly set if MD5 is used for non-security purposes.

Fix security finding B324 in test_samples/vulnerable_app.py:32. Issue: Weak MD5 hash used for security, risking cryptographic compromise.

ℹ️ Direct Use of `subprocess` Module

scanner/bandit_scan.py:9
bandit code_vulnerability B404
LOW

The `subprocess` module is imported, which, when used improperly, can lead to command injection vulnerabilities. Direct execution of external commands can be risky if inputs are not sanitized.

Risk: If user-controlled input is passed to `subprocess` functions without proper sanitization, an attacker could execute arbitrary commands on the system where the application is running, leading to remote code execution, data exfiltration, or system compromise.

Fix: Audit all calls to functions within the `subprocess` module. Ensure that any arguments derived from user input are properly sanitized and ideally passed as a list of arguments to avoid shell injection. Prefer `subprocess.run` with `shell=False` and a `command` list. Avoid `shell=True` entirely unless absolutely necessary and with robust input validation.

Fix security finding B404: Direct Use of `subprocess` Module in `scanner/bandit_scan.py` at line 9. Review `subprocess` module usage for potential command injection vulnerabilities, especially with untrusted input.

ℹ️ Execution of Process with Partial Executable Path

scanner/bandit_scan.py:27
bandit code_vulnerability B607
LOW

A process is initiated using a partial or relative executable path. This can lead to the execution of an unintended program if the system's PATH environment variable is manipulated or contains unexpected entries, allowing an attacker to hijack the execution flow.

Risk: If an attacker can control the system's PATH or place a malicious executable with the same name in a directory searched earlier, they could execute arbitrary code instead of the intended program, leading to privilege escalation or system compromise.

ℹ️ Subprocess Call with Untrusted Input and `shell=False` (Potential for Misuse)

scanner/bandit_scan.py:27
bandit code_vulnerability B603
LOW

A `subprocess` call is made without `shell=True`, which is generally safer, but still requires careful handling of untrusted input. If user input forms part of the command list, it can still lead to argument injection vulnerabilities.

Risk: Although `shell=False` mitigates shell injection, if untrusted input is used directly as elements in the command list, an attacker might be able to inject additional arguments or manipulate the command execution flow. This could lead to unintended command behavior or information disclosure.

Fix: Even with `shell=False`, thoroughly validate and sanitize all untrusted inputs that are passed as command arguments. Ensure that each argument is treated as a distinct item in the command list and that no single input can be parsed as multiple arguments or modify existing arguments. For complex commands, consider using a high-level API or a dedicated library if available.
